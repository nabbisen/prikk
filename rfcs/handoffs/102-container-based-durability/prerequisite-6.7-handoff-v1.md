# RFC 102 §6.7 — Index Prerequisite Handoff v1

**Cleared to answer §6.7 only.** Added to RFC 102 on 2026-08-13 after the owner chose **indexed lookup**.
**No design, no implementation, no production code.**

## 1. Why this exists

§6.4 established that preserving lock-free concurrent reads costs either linear-scan lookup or an index.
**The owner chose the index** — linear scan was rejected as bad for maintenance and unfit for a project
of this size; an advisory self-validating index was rejected for lacking correctness.

So object lookup stays sub-linear, and the design owes an index. **Three things must be known before
that design can be written**, and none of them could have been asked before the choice was made.

## 2. The questions

1. **Durability-bearing, or rebuildable?** If the index can be regenerated by scanning the container —
   Git's `.idx` is regenerable from a packfile — it stays **off the durability path**, and only
   concurrency remains. If not, it is another container and inherits §3's append/truncate requirement.
   **This changes the design's size materially.** Answer from what the container format would actually
   have to contain, not from what would be convenient.
2. **Which publication shape can this codebase actually support?** Two fit constraints the RFC already
   imposes:
   - **Append-only index** — no in-place mutation, so no torn read. §3's own idiom.
   - **A/B slots with a single-field publish** — §3.2 already mandates pre-created alternate slots for
     compaction, so the shape is already required elsewhere.

   Report what each costs and which the code can support. **Do not pick on elegance**, and do not treat
   my listing them as evidence either works.
3. **State the correctness property.** What must a reader always observe, and what must it never observe?
   Write the property the eventual proof will have to establish, before there is a design to prove it
   about — it is easier to state honestly now than after a design exists to defend.

## 3. Two corrections to carry, both mine

- **"Requires inventing a lock-free primitive" was overstated.** No precedent *in this codebase* is not
  the same as unprecedented — SQLite's WAL-index and LMDB's dual-meta-page solve this exact problem, and
  §6.1's survey already found those systems on container storage. **The cost is design plus a correctness
  proof, not invention.** Do not inherit the stronger framing.
- **§3's durability claim was wrong until 2026-08-13.** `atomic_replace` creates a temp name and renames,
  even over an existing name; only `durable_append`/`durable_truncate` avoid a rename. **If the index is
  durability-bearing, it must use the append/truncate idiom.** The correction is in §3; read it before
  answering question 1.

## 4. Standing

- **A stop-and-report is a complete outcome.** If neither publication shape can be made sound here, that
  is the finding, and it returns the lookup decision to the owner rather than being worked around.
- §6.1–§6.6 are complete and accepted; this is the seventh and last prerequisite before design.
- RFC 103 Increment B remains unauthorized — nothing on that track.
