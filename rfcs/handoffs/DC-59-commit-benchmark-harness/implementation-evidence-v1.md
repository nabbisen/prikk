## Design note: why each generated repository goes through two commits, not one

Not spelled out explicitly in the handoff, so recorded here. A genesis commit against an empty
baseline necessarily authors every file present — there is no way to hold "repository size" and
"changed-file count" independent on a first commit, since every file *is* the change. Both axes
therefore need a real baseline: generate the full repository, commit it (genesis, untimed), seal it
(untimed) — then mutate exactly the files under test and time only the following `commit`. This is
also why the fixed maintainer key from the handoff is needed even though the *timed* operation never
touches trust: only the untimed setup seal uses it. This does not conflict with the "cannot commit
twice" constraint — there is exactly one seal, entirely inside untimed setup, and exactly one timed
trial per generated repository; nothing is sealed *between* timed trials.

## Harness structure

- `SplitMix64` — deliberate duplicate of `hash_differential.rs`'s generator, not reachable from this
  crate (private, `#[cfg(test)]`, different crate). Documented as such in the module doc.
- `generate_tree` — deterministic file generation across a directory tree (breadth 8, depth 3),
  round-robin file placement so the tree is genuinely traversed, not concentrated in one directory.
- `setup_baseline_repository` — untimed: init, generate, genesis-commit, trust the fixed maintainer
  key, seal.
- `mutate_files` — deterministic content mutation of the first N generated files.
- `time_commit` — the one timed operation per generated repository.
- `commit_benchmark` — the `#[ignore]`d test itself; runs both axes plus the spawn-floor sample, then
  writes the report file directly, so the report is exactly what running the documented reproduction
  command produces.

## Axis A — repository size, 1 file changed

10 / 100 / 1,000 / 10,000 files, sample counts 5/5/5/3 (documented in the report; fewer samples at
10,000 to bound total harness runtime — stated, not hidden). Spans two orders of magnitude as
required.

## Axis B — changed-file count, fixed 1,000-file repository

1 / 10 / 100 / 1,000 changed files, 5 samples each. The size-1,000 point is shared with Axis A's
`1000 files, 1 changed` case; the two independently-measured runs are close (Axis A: 58.20 ms
median; Axis B: 57.77 ms median, same run) — a coherence check, not a formal cross-validation, and
not asserted as such in the report.

## The report

`rfcs/handoffs/DC-59-commit-benchmark-harness/benchmark-report-v1.md`, generated by the harness
itself (not hand-written), from:

```
cargo test -p prikk --locked --test dc59_commit_benchmark -- --ignored --nocapture commit_benchmark
```

The committed report is from this exact debug-profile command (not a `--release` run), so the
reproduction instructions inside the report are literally accurate for a from-scratch checkout.
Contains both curves as tables with sample counts, all generator parameters including the fixed
author and maintainer seeds, CPU model, filesystem type under the temp directory (`tmpfs` on this
machine — read from `df -T` at run time, not assumed), the process-spawn floor, where signing cost
sits, and the reproduction command. States no conclusion about NFR-PERF-01 compliance — that is
explicitly left to DC-56, per the handoff's "you are not deciding anything."
